# Assembly: OOP vs DOD

The compiled code for both variants is nearly the same. The difference in
speed and cache misses does not come from the instructions, but from the
addresses those instructions touch.

Source: `out/*.s`, generated by `scripts/run.sh` (Zig, `-OReleaseFast`,
`aarch64-linux-gnu`). `scripts/asm.sh` extracts the timed region, the code
between the two `clock_gettime` calls, into `results/asm.jsonl`. The results
page shows it side by side under the Assembly tab.

## The hot loop at `cold=60`

Per element, the inner loop increments one `u32`.

OOP (`src/oop.zig`, array of structs, 64 B per entity):

```
.LBB0_19:
    ldr   w13, [x12]          ; load health
    adds  x11, x11, #1        ; counter++
    add   w13, w13, #1        ; health + 1
    str   w13, [x12], #64     ; store, then advance by the entity size
    b.lo  .LBB0_19
```

DOD (`src/dod.zig`, struct of arrays):

```
.LBB0_18:
    ldr   w12, [x19, x11]     ; load health
    add   w12, w12, #1        ; health + 1
    str   w12, [x19, x11]     ; store
    add   x11, x11, #4        ; advance by 4 bytes
    cmp   x11, #1024, lsl #12 ; 4 MiB
    b.ne  .LBB0_18
```

## What the comparison shows

| | OOP | DOD |
|---|---|---|
| Instructions per element | 5 (6 at `cold=0`) | 6 |
| Data accesses per element | 1 load + 1 store | 1 load + 1 store |
| Stride between elements | entity size (16, 32, 64, 128 B) | 4 B |
| Vectorized | no (scalar `w` registers) | no (scalar `w` registers) |

- **DOD runs one more instruction per element and is still much faster.**
  OOP uses a post-indexed store that advances the pointer for free, while DOD
  needs a separate `add` and `cmp`. At `cold >= 28` the speed gap is driven by
  cache misses, not instruction count.
- **The stride is the only thing that changes with `cold`.** In OOP the
  immediate in `str w13, [x12], #N` is 16, 32, 64 and 128 for `cold` = 12, 28,
  60 and 124. The rest of the loop is identical. In DOD the loop never
  changes.
- **At `cold=0` both variants compile to the identical loop.** The entity is
  4 bytes, so the array of structs is the same array as `health`. This is why
  both variants report identical cachegrind numbers in that row.
- **Data references match.** Both do one load and one store per element, so
  total data references are almost equal (about 211M). The 0.5M gap comes from
  the initialization phase. OOP stores to each entity with a strided store,
  and DOD calls `memset` on the 4 MiB `health` array. I did not trace which
  `memset` stores are responsible, so treat that explanation as an inference.
- **Neither loop is vectorized.** Both use scalar 32-bit registers. DOD's
  unit-stride loop is the kind of loop that could use NEON. I did not
  investigate why the compiler did not, so this is an observation, not an
  explanation. If it were vectorized, DOD would execute fewer instructions
  still and the gap would widen.
- **DOD never touches the cold array.** The assembly allocates it (60 MiB at
  `cold=60`) and then calls `memset` only on the 4 MiB `health` array. OOP's
  initialization writes to every entity, so it touches every page of the
  array. This is a second, indirect effect on top of the cache lines.

## Takeaway

Reading the assembly rules out the compiler as the cause. The code for the
two layouts is almost equal, so the wall-clock gap (about 14x at `cold=124`)
and the 16x gap in L1 misses at `cold >= 60` come from the memory access
pattern: one useful 4-byte value per 16-128 byte stride against four bytes per
element. That matches the
explanation in [cache-notes.md](cache-notes.md).
